Bots at the shared table
========================
Deployed builds show Build <commit> beside the game code (inside Players and
Chronicle on phones), and in the gathering's Table details. The label is embedded
in the loaded app bundle and links to its deployment run. Its tooltip includes
the full PR head revision; an already-open older tab retains
its old label. Local builds without deployment metadata omit the label.

Open /play/ beneath the deployed site base. The old /practice/ URL redirects here.
Create a two-, three-, or four-player table, then open Invite friends.
Choose Money, Engine (current), or Engine (historical v4) and select Invite bot.
Each bot occupies one remaining seat. Human guests join with the ordinary link/code.
The host can also select a bot for their own seat under Table details / Your seat,
allowing an all-bot game. Seat assignments are fixed once drafting begins.

Select Begin when every seat is occupied. Each bot chooses a uniformly random
available leader on its draft turn. All players use the normal GameSession UI,
shared supply, ordinary multiplayer ending/tiebreak rules, and immutable events.
This replaces the separate local practice UI; it does not change multiplayer rules.
The bot strategies and leader opening books are the existing three opponents.
They have been tested for legal play at all table sizes; their historical balance
training and opening-book selection primarily used heads-up games.

Execution and recovery
----------------------
The host browser runs bot decisions in a worker. Keep that table open while bots
play. Other human clients receive the same committed moves as in any shared game.
Before submitting the next bot command, the host waits for the current move's
animations to finish and its destination cards to paint. Reduced motion skips
travel. This keeps fast bot turns from clearing slots while cards are still flying.
A host refresh rebuilds observations and policy memory from the event log and
resumes bot turns. Offline progress waits for the host to reconnect; a failed
worker or write offers Retry bot. Multiple host tabs cannot duplicate a move:
commands carry a stable bot/revision ID and an expected server revision.
The host may control only recorded bot seats, never another human seat.
The rules restrict inviting/automating seats to the gathering and preserve bot
metadata when a human joins. The bot controller is not an authoritative server;
the existing trusted-client game architecture remains in place.

The worker reconstructs game state from the same stream used by multiplayer.
Only the policy-facing observation is restricted: the policy receives its own
hand, public composition, public actions/history, and public resources/supply.
It receives neither shuffle seeds, hidden deck order nor opposing hand contents.
Human Undo restores the bot inventory/draw tracker as well as the shared game.

Validation
----------
Tests cover mixed and all-bot 2/3/4-player games, legal random drafts, replay/
refresh parity, human Undo, invitation races, retry idempotency, stale commands,
and raw unauthorized bot impersonation. Browser smoke uses real Auth/Firestore
emulators and the normal table, including all three policies and host reload.
The illustrated 012-bot-seats story covers inviting, drafting, taking turns and
refreshing through the real UI. Desktop/phone captures are visually reviewed.

Local commands (all through nix develop)
- bun run check
- bun test ./tests/tooling/table-bots.test.ts
- bun run test:backend
- Build with the demo Firebase emulator variables, then bun run test:bot-table.
- E2E_STORY_FILTER='invite an Engine bot' bun run test:e2e

Deployment needs both the frontend and updated Firestore rules in the preview
project. PR preview deployment includes the versioned policy source directories.
